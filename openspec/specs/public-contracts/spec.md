# Public Contracts Specification

## Purpose

Define the compatibility and migration guarantees for supported public CLI,
Python, schema, artifact, advisor, and MCP surfaces.

## Requirements

### Requirement: Compatibility Surface Inventory

Every retained command alias, Python wrapper, and transitional compatibility
behavior SHALL have a documented status, canonical replacement, and support
window.

#### Scenario: A user adopts a retained wrapper

- **GIVEN** an application imports a documented compatibility wrapper
- **WHEN** the user reviews migration guidance
- **THEN** the canonical import is identifiable
- **AND** the minimum supported lifetime is explicit

#### Scenario: A retained surface is deprecated

- **GIVEN** maintainers plan to remove a supported alias or wrapper
- **WHEN** deprecation begins
- **THEN** migration guidance and a changelog notice are published
- **AND** the surface remains for at least one feature release and 90 days
- **AND** removal does not occur before the documented major-version boundary

### Requirement: Public Stability Map

The documentation SHALL identify the stability status, owner, compatibility
rule, and contract gate for every supported public integration surface.

#### Scenario: A maintainer reviews a public change

- **GIVEN** a proposed change affects Python imports, CLI, MCP, `DatasetSpec`,
  advisor JSON, or generated artifacts
- **WHEN** the maintainer consults the stability map
- **THEN** the affected owner and contract gate are identifiable
- **AND** the change can be classified as additive or breaking

#### Scenario: An experimental integration is used

- **GIVEN** a provider adapter or runnable example is not part of the stable
  deterministic core
- **WHEN** its compatibility status is reviewed
- **THEN** it is clearly labelled experimental
- **AND** core safety requirements still apply

### Requirement: Versioned Golden Contract Catalog

Every golden public JSON and MCP fixture SHALL have an explicit contract
version and compatibility rule.

#### Scenario: A fixture is added

- **GIVEN** a new public contract fixture is checked in
- **WHEN** contract tests run
- **THEN** the fixture must be registered in the versioned catalog
- **AND** its change rule must be `additive_only` or `schema_versioned`

#### Scenario: A contract changes

- **GIVEN** a golden fixture differs from its reviewed baseline
- **WHEN** the change is assessed
- **THEN** additive-only changes preserve all existing valid consumers
- **AND** breaking schema-versioned changes advance the serialized version and
  provide migration guidance

### Requirement: Previous Feature Release Compatibility

The current package SHALL read reviewed specs and generated metadata from the
previous feature-release compatibility baseline.

#### Scenario: A previous reviewed spec is loaded

- **GIVEN** an immutable spec and manifest copied from an annotated release tag
- **WHEN** the current package loads the artifacts
- **THEN** their schema version and fingerprint remain valid
- **AND** deterministic generation produces the expected entity row counts
- **AND** the new bundle remains synthetic and source-row-free

#### Scenario: The baseline advances

- **GIVEN** maintainers select a newer previous-release baseline
- **WHEN** fixtures are added
- **THEN** they are copied into a new versioned directory with tag and commit
  provenance
- **AND** existing baseline files are not regenerated by current models

### Requirement: Runtime And Integration Support Policy

The project SHALL document the release-gated Python versions, optional extras,
and provider-adapter maturity independently from internal implementation
details.

#### Scenario: A user selects an installation profile

- **GIVEN** a user needs the base package or an optional capability
- **WHEN** the user consults the support policy
- **THEN** each extra's capability and release gate are identifiable
- **AND** the `all` extra is not presented as the normal user installation

#### Scenario: A maintainer changes runtime support

- **GIVEN** a proposed change drops a Python version, removes an extra, or
  changes a supported provider adapter
- **WHEN** the compatibility impact is reviewed
- **THEN** the change is classified as breaking
- **AND** notice, migration, and security-exception rules are explicit

#### Scenario: A provider adapter is evaluated

- **GIVEN** a provider-specific adapter before the 1.0 baseline
- **WHEN** its support status is reviewed
- **THEN** it is distinguished from the versioned provider-neutral contract
- **AND** metadata-only, validation, dependency, fake-test, and redaction
  requirements remain mandatory

### Requirement: Bounded Provider Response Parsing

Optional external advisor adapters SHALL apply a finite local byte budget to
structured response text before application JSON/Pydantic parsing.

#### Scenario: Provider response is within budget

- **GIVEN** an external advisor returns non-empty structured response text
- **WHEN** its UTF-8 size is within the configured response budget
- **THEN** the application may parse and validate it against the typed response
  model
- **AND** per-call metadata records the measured bounded response size

#### Scenario: Provider response exceeds the budget

- **GIVEN** an external advisor returns response text larger than the configured
  byte budget
- **WHEN** the application receives the response
- **THEN** it rejects the response before application JSON/Pydantic parsing
- **AND** no proposal is returned or applied
- **AND** public errors and per-call metadata do not retain provider text,
  credentials, source literals, or nested provider exceptions

### Requirement: Bounded Local JSON Import

Local JSON dataset, profile/spec, and profile-cache importers SHALL enforce a
finite structural-depth budget before application JSON/Pydantic materialization.

#### Scenario: JSON structure is within budget

- **GIVEN** a byte-bounded local JSON document
- **WHEN** its object and array nesting is within the configured depth budget
- **THEN** the application may parse and validate it
- **AND** structural characters inside JSON strings do not count as nesting

#### Scenario: JSON structure exceeds the budget

- **GIVEN** a local JSON document whose structure exceeds the configured depth
  budget
- **WHEN** a dataset, profile/spec, or profile-cache importer receives it
- **THEN** the document is rejected before application JSON/Pydantic parsing
- **AND** no partial dataset, profile, spec, or cache value is returned

### Requirement: Cross-Interface Acceptance Has Explicit Coverage

Final acceptance of the source/output and MCP work SHALL cover every supported
source, output and mode composition through installed Python, CLI and real stdio
MCP. It SHALL inventory every public option and rule family, test their boundaries
and interactions, and distinguish native interface capabilities from composed
safe-profile/reviewed-specification handoffs.

#### Scenario: A source has no native MCP acquisition tool

- **GIVEN** a supported source can supply a safe profile or reviewed DatasetSpec
- **WHEN** its MCP generation matrix cell executes
- **THEN** the handoff and acquisition interface are recorded explicitly
- **AND** the actual installed MCP tool generates and revalidates the requested output
- **AND** absence of a convenience flag does not excuse missing shared semantics

#### Scenario: An option or tool is added

- **GIVEN** public schemas, parser and discovery contain a new option or tool
- **WHEN** the expected acceptance inventory is reconciled
- **THEN** missing required coverage fails the inventory check
- **AND** compatible pairs, boundaries and relevant high-risk interactions receive cases

#### Scenario: An identifier distribution retains a legacy prefix

- **GIVEN** a reviewed specification includes `synthetic_identifier.prefix`
- **WHEN** synthetic identifiers are generated or the option inventory is reconciled
- **THEN** the property is documented as retained metadata, not a generation control
- **AND** string tokens keep the mandatory `synthetic_` plus ASCII integer namespace
- **AND** the supplied prefix is never copied into generated values

#### Scenario: A tiny exact decimal is exported as CSV

- **GIVEN** a valid reviewed DECIMAL field produces a value represented internally with an exponent
- **WHEN** a typed synthetic CSV bundle is written and independently reloaded
- **THEN** the CSV numeric cell uses exact plain decimal notation
- **AND** standalone validation preserves the declared precision and scale
- **AND** arbitrary exponent-form input strings do not gain new parsing permission
- **AND** formatting rejects unbounded exponents and non-finite values before expanding text

#### Scenario: A signed exact decimal uses the maximum scale

- **GIVEN** a reviewed DECIMAL field declares precision 38 and scale 38
- **WHEN** the smallest or largest fractional magnitude is parsed with either sign
- **THEN** the bounded plain-text parser admits the sign without consuming digit precision
- **AND** out-of-precision, exponent-form and oversized inputs remain rejected

#### Scenario: Decimal text expansion exceeds the supported width

- **GIVEN** a Decimal scalar has an unbounded exponent or a non-finite value
- **WHEN** validation or CSV, JSON, Parquet or SQL serialization handles it
- **THEN** the shared decimal conversion rejects before fixed-point text allocation
- **AND** typed Parquet and its controlled-invalid fallback enforce the same bound
- **AND** rejection contains no cell value and publishes no partial output
- **AND** valid signed scale-38 values retain their exact representation

### Requirement: Acceptance Evidence Separates Execution And Authority

Acceptance evidence SHALL bind results to the exact commit, built artifacts and
environment. It SHALL distinguish mocked acquisition, disposable fictional live
databases, automated SDK execution, actual human client review and separately
gated transformation authority. Missing required execution SHALL remain blocked.

#### Scenario: An existing synthetic plan is continued in an actual client

- **GIVEN** a prepared plan remains after its interactive client closes
- **WHEN** the existing conversation is resumed with the same connection and tool policy
- **THEN** the client inspects that workspace without replaying planning or deleting evidence
- **AND** the full current specification is available for human review before fresh specific consent
- **AND** actual event references and exact-file hashes bind review and consent before approval
- **AND** client resume is distinct from state-requested dataset recovery
- **AND** configuration preflight, model summaries and assistant turn completion do not establish human review or process teardown

#### Scenario: An installation or integration cannot run

- **GIVEN** a required case lacks dependencies, environment or actual execution
- **WHEN** the final report is produced
- **THEN** its status is blocked, not passed or silently skipped
- **AND** N/A is reserved for a documented contract exclusion with its supported
  alternative route where shared generation semantics apply

#### Scenario: A confirmed failure requires a repair

- **GIVEN** the implementation changes after a campaign run
- **WHEN** acceptance is reconsidered
- **THEN** earlier exact-commit acceptance is superseded
- **AND** affected cases and the final full gate run on the final SHA
- **AND** existing independent release and local human approval requirements remain
  separate and cannot be replaced by an automated test result
